## 1. Tier 1 verdicts

### S0a — `GET /jobs/{jobId}/artifacts/vpr/export` has no ownership check
**VERDICT: CONFIRMED — proven by execution, no deploy required.**

OBSERVATION (code). `src/backend/careervp/handlers/export_handler.py:113-120`:
`_read_artifact` takes `user_id` and passes it to the `cover_letter`,
`interview_prep` and `cv_tailored` branches. The `vpr` branch calls
`_read_vpr(job_id)` — `user_id` is dropped. `_read_vpr` (`:123-133`) reads
`results/{job_id}.json` from `VPR_RESULTS_BUCKET_NAME` with no scoping.

OBSERVATION (route is live). `aws apigateway get-resources --rest-api-id ymzhvcxod0`
returns the resource `/jobs/{jobId}/artifacts/{moduleType}/export` with `GET` and
`OPTIONS`. `get-method` on it returns
`{"auth": "COGNITO_USER_POOLS", "authorizerId": "9oadeg", "validator": null}` —
so it is deployed, and it is authenticated but not authorized.

OBSERVATION (upstream guard search). No WAF rule, resource policy or authorizer
scopes by resource owner; the Cognito authorizer only proves *an* identity.

OBSERVATION (execution). A scratch moto test built on the project's own P-05
harness: victim VPR seeded to S3, attacker authenticated with real Cognito claims
for a *different* `sub`, requesting the victim's `jobId` with `moduleType=vpr`:

```
S0a status=200
S0a attacker received presigned URL: https://p05-artifacts-bucket.s3.amazonaws.com/exports/vpr/victim-job-0001/victim...
S0a victim secret present in exported DOCX: True
```

The attacker received HTTP 200, a presigned S3 URL, and the DOCX at that URL
contained the victim's confidential VPR text.

**What the human should do.** One-line fix: pass `user_id` into `_read_vpr` and
scope the read (the VPR's owner is available both in the jobs table and in the S3
payload's `user_id` field). Fix S0b in the same change — same handler family, same
class. Then extend the P-05 registry (see §4/P4) so `moduleType` is parameterised
across **all four** branches, or this reopens silently.

### S0b — VPR status S3 fallback sits above the ownership check
**VERDICT: mechanism CONFIRMED by execution. Stated trigger (24h TTL) REFUTED.**

OBSERVATION (code). `handlers/vpr_status_handler.py:542-558`. `get_job` is called
at `:542`; when it returns `None`, `:547` calls `_try_build_response_from_s3(vpr_id)`
— no `user_id` parameter — which returns the enriched VPR plus a presigned URL
(`:592-617`). The owner comparison is at `:555-558`, **below** the fallback, so it
guards only the DynamoDB branch.

OBSERVATION (execution, with a matched control):

```
CONTROL (job row present): status=403
CONTROL body={"error": "User can only access own VPRs", "status_code": 403}

S0b (job row absent / TTL expired): status=200
S0b victim secret in body: True
S0b presigned download_url issued: True
```

The ownership check demonstrably works when the row exists, and is demonstrably
bypassed when it does not.

**REFUTED sub-claim — the 24h TTL premise.** The inventory says the jobs row
"TTLs out at 24h (`jobs_repository.py:475`) while the S3 object persists", so
"for any VPR older than 24 hours, any authenticated caller with the `vprId` gets
the owner's content." That is wrong.

- OBSERVATION: `jobs_repository.py:473-475` does set `now + 24*3600` — **but only
  when the caller supplies no `ttl`**, i.e. at job *creation*.
- OBSERVATION: `handlers/vpr_worker_handler.py:536-548` — on completion the worker
  passes `ttl=one_year_ttl` where `one_year_ttl = now + 365*24*3600`. A *completed*
  VPR (the only kind with an S3 result to leak) has its row extended to a year.
- OBSERVATION (live devx): all 10 ttl-bearing rows in `careervp-jobs-table-devx`
  carry 365-day windows; `ttl already elapsed but row still present: 0`; and all
  6 sampled S3 results from 2026-08-01/03 still have their jobs rows:
  `374788f8-… -> jobs-row-owner: 848834a8-…` etc.

INFERENCE: the "every VPR older than 24h is exposed" framing is false. The real,
always-available trigger is the one the inventory mentions only in passing
(A7.4): `jobs_repository.py:217-223` returns `None` on any `ClientError`, so a
single transient DynamoDB error drops the caller into the unguarded S3 branch
*inside* any window. The 365-day TTL is the second trigger.

OPINION: severity is unchanged (it is still a live cross-tenant read), but
urgency framing should shift from "time-bomb on old data" to "throttle-triggered,
any data, any time".

### S11d — CV upload 500s whenever the parser extracts a GPA
**VERDICT: CONFIRMED at the DAL layer. Live user impact UNPROVABLE-WITHOUT-DEPLOY.**

OBSERVATION (code). `models/cv.py:92` — `gpa: Annotated[float | None, …]`.
`dal/dynamo_dal_handler.py:99-105` — `save_cv` does
`model_dump(exclude_none=True, mode='json')` then `put_item`, and the catch at
`:106` is `except (ClientError, ValidationError)`. `_convert_floats_to_decimal`
exists at `:889` and `save_cv` does not call it.

OBSERVATION (execution, moto):

```
NO-GPA: save_cv succeeded
GPA: save_cv raised builtins.TypeError: Float types are not supported. Use Decimal types instead.
```

`TypeError` is not in the catch tuple, so it escapes `save_cv` entirely.

OBSERVATION (blast radius). `handlers/cv_upload_handler.py:186-224` — both the
users-table write and the cvs-table write are wrapped in `except Exception`, and
since commit `7cdc5e5` the cvs-table failure returns **HTTP 500**
(`'Failed to persist parsed CV'`). So a GPA-bearing CV fails the upload.

REFUTED sub-claim. The inventory calls `save_vpr` (`:296-315`, `cost_usd: float`)
the "same omission". The code is identical in shape, but OBSERVATION:
`grep -rn "\.save_vpr(" src/backend/careervp` returns **zero non-test callers** —
VPR results are persisted to S3 and to the artifacts table by other paths. The
`save_vpr` float bug is real but unreachable.

**Why "live impact" is not proven.** The defect fires only if the parser actually
emits a `float` for `gpa`. That depends on LLM output shape on a real CV. I did
not run the live parser (that needs a deploy or an API key + real document).
UNPROVABLE-WITHOUT-DEPLOY: upload a GPA-bearing CV to devx and observe the 500.

**What the human should do.** One-line fix (`save_cv` calls the converter that
already exists two hundred lines below it) with a regression test asserting a
`Decimal` round-trip. Cheap, low-risk, do it regardless of the live-impact
question.

### S25 — the gap-analysis state machine has never advanced
**VERDICT: CONFIRMED (the call is broken). "Never advanced" REFUTED as written.**

OBSERVATION (key schema). `dal/application_repository.py:85-98` — `update_state`
keys on `{'userId': user_id, 'applicationId': application_id}` with
`ConditionExpression='attribute_exists(userId) AND attribute_exists(applicationId) AND #state = :expected_state'`.

OBSERVATION (the argument). `handlers/gap_handler.py:874-882`:
```python
application_repo.update_state(
    application_id=application_id,
    user_id='',
    new_state='gap_questions_pending',
    expected_state='cv_selected',
)
except Exception:
    pass
```
`user_id=''` is literal, and the handler *has* the real `user_id` in scope.

OBSERVATION (execution, moto, with a control):
```
CONTROL: state advanced to gap_questions_pending
EMPTY-USER: raised ConditionalCheckFailedException: The conditional request failed
EMPTY-USER: real item state after call = cv_selected
```
So the transition is correct when given a real `user_id`, and fails every time
with `''`, leaving the record at `cv_selected`. The `except Exception: pass` at
`:881` swallows it.

REFUTED sub-claim. "Applications stall at `cv_selected` forever" is not what the
live data shows. OBSERVATION (live devx scan of `careervp-applications-table-devx`):
```
total: 12
Counter({'gap_responses_submitted': 8, '<missing>': 4})
```
Zero rows are at `cv_selected`; 8 have advanced past `gap_questions_pending`.
INFERENCE: another path writes the state — `update_gap_responses`
(`application_repository.py:114-140`) is an **upsert** that sets `#st` via
`if_not_exists`, so the record reaches `gap_responses_submitted` without ever
passing through the broken transition. The state machine is not stalled; it is
**bypassed**, and the `expected_state` guard it exists to enforce is not enforcing
anything.

OPINION: this is worse than the inventory's version, not better. A stalled
machine is visible; a bypassed one silently invalidates every downstream
assumption that a state was reached legitimately.

### S23 — O(n×m) tokenizer on the request path
**VERDICT: mechanism CONFIRMED. "On the request path" REFUTED. Severity REFUTED.**

OBSERVATION: `logic/vpr_generator.py:971-985` — `_select_best_evidence` loops the
whole `evidence_pool` per requirement and calls `_text_tokens(evidence)` each
time with no memoisation; `:297-304` calls it once per `job_requirements` entry.
So tokenisation runs `len(requirements) × len(evidence_pool)` times, and
`:281-287` accumulates every achievement from every role with no cap — both as
claimed.

OBSERVATION (measured, real function, synthetic inputs):
```
20 reqs x 50 evidence  = 1000 pairs  ->   3.4 ms
40 reqs x 200 evidence = 8000 pairs  ->  26.9 ms
60 reqs x 500 evidence = 30000 pairs -> 102.4 ms
```

REFUTED: "on the request path". VPR generation is the one pipeline that *was*
moved async (the inventory says so itself in R5) — this runs in
`vpr_worker_handler`, behind SQS, not behind API Gateway's 29s cap.

OPINION: at ~0.1s for a pathological CV, sitting next to multi-second LLM calls,
this is not worth an engineering hour. Fixing it is a one-line `dict` memo if
someone is already in the file; scheduling it as work would be waste.

### The base rate

Across the 12 sampled findings (10 defect claims + 2 good claims), and adding the
4 Tier-1 findings, **14 defect claims** were adjudicated:

| Outcome | Count | Share |
|---|---|---|
| A real defect exists at the core of the claim | **14 / 14** | 100% |
| …but carries at least one materially wrong sub-claim (premise, trigger, severity, mechanism, or citation) | **6 / 14** | 43% |
| Fully refuted (no defect at all) | **0 / 14** | 0% |
| Undecidable without a deploy | **0 / 14** | 0% |

The six with a wrong sub-claim: S0b (24h TTL trigger — actually 365 days), S25
("never advanced" — actually bypassed), S11d (`save_vpr` sibling — unreachable),
S2 (exploitable via HTTP API v2 — no such API exists), S23 (on the request path,
high severity — async path, ~0.1s), S26 ("unbounded" — capped at 2500 words).
S10's mechanism and S7's line number were also slightly off but did not change the
conclusion.

> **INFERENCE for the ~85 un-sampled findings.** The inventory is **reliable about
> existence and unreliable about explanation.** If the sample holds, essentially
> every remaining finding points at something genuinely wrong — so none should be
> dismissed unread — but roughly four in ten carry a wrong trigger, severity, or
> mechanism, and two of the six errors I found (S0b, S25) were the kind that would
> have sent the fix in the wrong direction or mis-ranked the queue.
>
> **OPINION — the operating rule this implies:** treat every inventory entry as a
> *reliable pointer to a location* and an *unreliable description of the problem*.
> Re-derive the mechanism at the file before writing any fix, and never let an
> inventory sentence justify a severity ranking. The per-finding cost of that
> re-derivation was 5-20 minutes in this session; the cost of skipping it is the
> multi-day wrong-fix this project has already paid for more than once.
>
> Notably, **zero** findings were fully fabricated — which is a meaningfully
> better result than the P0 calibration example (the CFN-ownership false alarm)
> would have predicted. That false alarm was an *instrument* error, not an
> analysis error, and no comparable instrument error appeared in this sample.
