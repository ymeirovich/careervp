## 🗳️ AWS CloudFormation Deployment Engineer

### Position

CloudFormation will do what the template graph tells it to, not what the register hopes: the register's three "instant" rollback claims are all soft (they require a full `cdk deploy` of a ~476/500-resource stack plus a new API GW Deployment, and one lever — `AUTHORIZER_DISABLED` — appears to be dead wiring), and its P-26 mitigation "retained logical id" is impossible across a stack boundary. The only guardrails that bind a subagent swarm are ones CloudFormation itself enforces: stack policy, termination protection, deletion protection, and a change-set two-phase deploy where agents can `CreateChangeSet` but only a human can `ExecuteChangeSet`.

### Key points

- **Q1 — Mechanical guardrails (before any 🔴/🟠 deploy).** Discipline doesn't survive a swarm; use controls the CFN service enforces regardless of who deploys:
  1. **Stack policy** on `CareerVpCrudDev` (and DB/S3 stacks) denying `Update:Replace`/`Update:Delete` on the RestApi logical id (`service-rest-api…`), all `AWS::DynamoDB::GlobalTable`s, buckets, and the Cognito pool (`aws cloudformation set-stack-policy`). This makes an accidental RestApi replacement (LM-1's trigger, P-26) *fail the update* instead of orphaning `api.dev.careervp.com`. Note stack policies don't reach into nested stacks — protect the parent's `AWS::CloudFormation::Stack` resources too.
  2. **Termination protection** on every stack; **`deletion_protection`** on tables (P-12 first — PITR is already on per `api_db_construct.py:97`, deletion protection is not).
  3. **Change-set two-phase deploy as the only path**: `cdk deploy --method prepare-change-set --no-execute`; the agent IAM role gets `cloudformation:CreateChangeSet` but **not** `ExecuteChangeSet`. The change set's per-resource `Replacement: True/False` is CFN's *own* computation — strictly stronger than `cdk diff` string-heuristics the register leans on (§P-26 "run cdk diff and confirm zero replacement"). This is the mechanical form of the golden rule (scope-lock §9.2): a swarm physically cannot execute two changes, or any change, without a human keystroke.
  4. **LM-1 compensating control** (cdk diff is blind — the mapping isn't in any template): (a) read-only discovery now (`aws apigateway get-domain-names`, `get-base-path-mappings --domain-name api.dev.careervp.com`, Route53 record) committed as evidence per §6; (b) a synthetic canary/health-check on `https://api.dev.careervp.com/health` alarming within 1 min; (c) a one-line remap runbook (`aws apigateway update-base-path-mapping --domain-name … --rest-api-id <new> --stage <stage>`). Prefer `cdk import` of the `AWS::ApiGateway::DomainName` (importable) so the mapping becomes IaC-visible; until then the stack policy is the prevention and the canary the detection.
  5. **LM-2 compensating control**: a synth-time `aws_cdk.assertions` pytest gate (wired into the deploy wrapper, not a checklist) asserting every `AWS::S3::Bucket` CorsConfiguration and the OPTIONS mock-integration response VTL contains the exact live Amplify origin, plus a **post-deploy live preflight**: `curl -si -X OPTIONS https://api.dev.careervp.com/vpr -H "Origin: https://<branch>.<appid>.amplifyapp.com" -H "Access-Control-Request-Method: POST"` asserting the origin is echoed. This closes the register's own F-01 requirement (§3 LM-2) mechanically.

- **Q2 — Backups & rollback, per clause, with the register's claims challenged:**
  - **P-26 (🔴):** Snapshot `get-template` + `list-stack-resources` for all stacks, the RestApi id/stage, domain + base-path mapping JSON, Route53 record. **Challenge:** the register's "keep the old RestApi live until the new one is verified" is *not achievable inside a single-stack replacement* — CFN's cleanup phase deletes the old RestApi in the same update. It's only achievable blue/green: create the new API as a *separate* resource/stack, verify via its raw `execute-api` URL, then re-point the base-path mapping (seconds, and reversible in seconds). Also, "prefer a retained logical id" (§5 P-26 mitigation) is wrong across stacks: CFN resource identity is *(stack, logical id)* — moving the RestApi into a nested stack is always delete+create no matter what logical id you keep. The RestApi must not move; only auto-named resources (alarms/dashboards) can — the code already knows this (`api_construct.py:2024-2033` documents the physical-name "resource already exists" failure mode).
  - **P-10 (🔴):** Backup = git tag + `get-template`. **Challenge "revert to ALL_ORIGINS — instant":** the preflight lives in CFN Mock-integration OPTIONS methods; revert = code change + `cdk deploy` + a new `AWS::ApiGateway::Deployment` (5–15 min on this stack), **plus** browsers cache the bad preflight for up to `max_age=Duration.hours(1)` (`api_construct.py:335`). Pre-stage a revert branch, and *ship a small prior deploy lowering max_age to ~60s* before tightening. Verify revert via the live preflight curl + one real FE flow.
  - **P-04 (🔴):** Snapshot every Lambda's env (`aws lambda get-function-configuration` loop → JSON) and `describe-user-pool`. **Challenge "AUTHORIZER_DISABLED revert is instant, single env var" hard:** (a) the var exists on exactly **one** Lambda (`api_construct.py:1720`, cv_tailoring) and **no backend code under `src/backend/careervp` reads it** — the lever may be inert; (b) the actual gateway enforcement is `AuthorizationType.COGNITO` attached per-method (`api_construct.py:2795`), and changing that is a template change + new API deployment, i.e. minutes, not instant; (c) P-04 as scoped *removes* the flag — once removed, rollback is git-revert + redeploy. Sequence must be **flip-then-remove**: flip enforcement in one deploy while keeping the bypass code, soak against CloudWatch 401 rate, remove code a wave later. Out-of-band `update-function-configuration` is seconds but creates drift the next `cdk deploy` silently stomps — a subagent deploying an unrelated wave would *re-break* what a human emergency-reverted; make `detect-stack-drift` a pre-deploy gate.
  - **P-08 (🟠):** `aws s3api get-bucket-cors --bucket <cv-upload-bucket>` saved to file; revert via `put-bucket-cors` genuinely is seconds (S3 CORS isn't deployment-gated) — the one "instant" claim that survives, modulo the ~50 min browser cache (`max_age=3000`) and the same drift caveat. Enable versioning on the upload bucket (only the VPR results bucket is versioned, `api_db_construct.py:552`).

- **Q3 — §7 order is directionally right; three amendments.** (0) *New step 0, autonomous-safe:* stack policy + termination protection + snapshot pack + P-12 + the LM-1/LM-2 evidence reads and assertion tests — all read-only or 🟢. (1) Wave-0/oracle as written — autonomous OK. (2) **Do P-08 before P-10** (same allow-list content, but piloted on the surface that reverts in seconds), and precede P-10 with the max_age-60s deploy; gate both on the assertion test + live preflight; **human executes the change set**. (3) P-04 flag-flip only after the token-flow audit *and* after confirming what actually enforces auth in the live stack (see above — don't trust the register's model of the flag); human-in-loop, watch 401 rate ≥24h (bump the ONE_DAY access-log retention first or your evidence evaporates). (4) P-26 last, redefined as "decompose *around* the RestApi, never move it"; the base-path remap step, if ever needed, is human-only. Per step the smoke test is one script: DNS + `GET /health` 200 via `api.dev.careervp.com` + preflight from the Amplify origin + presigned-PUT preflight + authenticated hub read — run *before* (baseline green) and after every execute.

### Risks & blind spots

- **The register understates the physical-name minefield in P-26.** Nearly every Lambda uses an explicit `function_name` (20+ occurrences); any stack move is delete+create under the same name → `CREATE_FAILED: resource already exists`, mid-update rollback on a near-limit stack. The codebase comment at `api_construct.py:2029` and the memory note about the "physical-name import migration" already prove this bites here.
- **CFN cleanup-phase semantics:** if the clickops base-path mapping blocks (or doesn't block) the old RestApi delete, you end in either a stuck cleanup or a silently dangling `api.dev.careervp.com` returning `{"message":"Forbidden"}` — neither is a rollback; both look like "the swarm destroyed dev."
- **P-04 will masquerade as P-10.** Gateway-authorizer 401s bypass the Lambda that sets CORS headers; the existing `GatewayResponse` CORS (`api_construct.py:393`, ACAO `'*'`) currently saves you — if P-10 "locks down origins" also touches those gateway responses to a static origin, every auth failure becomes a browser CORS wall and the team will debug the wrong clause.
- **Omitted backups:** Amplify branch env vars (`aws amplify get-branch` — W1 lives only there), Route53 zone export, Cognito user export (`list-users`) — the pool is the one resource with *no* restore path; any P-07/P-24 property change that CFN classifies as replacement deletes every user. Check the change set's Replacement flag on the pool before any Cognito-touching execute.
- My lens can't verify the live account (deployed template may differ from `db-redesign` HEAD — e.g. whether gateway auth is actually enforced today); the §6 read-only evidence pass must precede everything. **Do-first:** ① stack policy + termination protection today, ② P-12 + snapshot pack, ③ LM-1 discovery + remap runbook, ④ LM-2 assertion test + smoke script, ⑤ change-set-only IAM split for agents — then, and only then, Wave 1.

### Confidence

`high` — the CFN replace/cleanup/logical-id semantics and the code-level findings (single dead-looking env var, per-method COGNITO attachment, 1-hour preflight cache, physical-name comments) are read directly from the repo; only the live-account state remains unverified.

## 🗳️ DR / Backup / Rollback Specialist

### Position

The register's threat model is right but its rollback claims are optimistic and, in one case, provably wrong against the code: every stateful resource in this stack carries `RemovalPolicy.DESTROY` (tables *and* buckets with `auto_delete_objects=True`), the "instant" `AUTHORIZER_DISABLED` lever has **no consumer anywhere in the backend** (it is set once, on one Lambda, at `api_construct.py:1720`, and never read), and nothing mechanical stops a subagent from executing a destructive deploy. Treat P-12 + IAM-gated deploys + a pre-tested revert drill as hard prerequisites — not "first safe slice" niceties — before any 🔴/🟠 clause ships.

### Key points

- **Q1 — Protect what exists, mechanically.** Discipline doesn't survive a subagent swarm; IAM and CloudFormation do. (a) **Deploy-credential split**: subagents run under a profile that allows `Describe*/Get*/List*/cloudformation:CreateChangeSet` but **denies** `ExecuteChangeSet`, `UpdateStack`, `lambda:UpdateFunctionConfiguration`, `apigateway:PATCH/PUT/DELETE`, `cognito-idp:*`, `route53:ChangeResourceRecordSets`. Agents can synth, diff, and stage change sets; only a human-held role can execute — that is "one reversible change at a time" enforced by AWS, not by prompt text. (b) **Stack policy + termination protection** on the live stack denying `Update:Replace`/`Update:Delete` on `AWS::DynamoDB::*`, `AWS::S3::Bucket`, `AWS::ApiGateway::RestApi`, `AWS::Cognito::UserPool` — closes the gap where an agent renames a logical id and CFN silently replace-deletes (with `DESTROY`, the *old* resource and its data are deleted on replacement, per every table in `api_db_construct.py:97-433`). (c) **LM-1 compensating control** (cdk diff is blind — the domain isn't in the template): capture `aws apigateway get-domain-names` + `get-base-path-mappings --domain-name api.dev.careervp.com` + the Route53 record as a versioned evidence file *now*; then make the P-26 gate a script that asserts the base-path mapping's `restApiId` equals the live RestApi id **after** deploy, with the one-line revert (`update-base-path-mapping --patch-operations op=replace,path=/restApiId,value=<OLD_ID>`) pre-written and pre-tested. (d) **LM-2 compensating control** (a wrong CORS list synths as a valid template): a **runtime** preflight probe — `curl -X OPTIONS -H "Origin: https://<branch>.<appid>.amplifyapp.com"` against the deployed stage asserting the ACAO echo — as a required post-deploy gate, *in addition to* a synth-time template assertion. Template assertion alone is insufficient because API Gateway's generated preflight mock does exact-origin matching: the register's own proposed list `["https://*.amplifyapp.com"]` (P-10 card) may pass a template check and still fail in the browser — wildcard subdomains behave differently at API GW than in S3 CORS (`api_db_construct.py:568` works; the same string in `CorsOptions.allow_origins` may not).

- **Q2a — What to snapshot before each clause.** Before **any** 🔴: git-tag the deployed `ui-upgrade` commit, save the live template (`aws cloudformation get-template`) + `describe-stacks` outputs + full `aws apigateway get-resources`/`get-stage` dump to the backups bucket — that is your whole-stack golden point (CFN keeps no history for you). Then per clause — **P-26**: on-demand DynamoDB backups of every table (`create-backup`; they survive table deletion indefinitely, unlike PITR whose window here is shortened to **7 days**, `recovery_period_in_days=7`, and whose restore lands in a *new* table needing stream/ESM/env rewiring — PITR is an RPO tool, not a fast-RTO tool); `aws s3 sync` the upload bucket (it is `versioned=False`, `api_db_construct.py:169`, with 30-day expiry — versioning saves nothing there, and `auto_delete_objects=True` purges *all versions* everywhere else); the LM-1 domain/mapping evidence file. **P-10**: the current stage's CORS behavior (baseline preflight probe outputs) + the Lambda-layer ACAO config (the real ACAO on non-OPTIONS responses comes from Lambda per the comment at `api_construct.py:326` — two places must revert together). **P-04**: `describe-user-pool` + app-client config, the Amplify branch env (`aws amplify get-branch` — the four wires live in Amplify console, outside CDK, and nobody is snapshotting them), and a captured working token-flow HAR from the live FE. **P-08**: `get-bucket-cors` JSON of the upload bucket saved verbatim (revert = `put-bucket-cors` with the saved file — seconds, no CFN, though it creates drift you must reconcile next deploy).

- **Q2b/c — The "instant revert" claims don't survive contact with the code.** (1) **P-04**: the register says revert = "set `AUTHORIZER_DISABLED=true` — instant, single env var." In this repo the flag is set on exactly one function (cv-tailoring) and **grep finds zero readers** in `src/backend/careervp`; meanwhile protected routes are wired with `AuthorizationType.COGNITO` at the gateway (`api_construct.py:2740-2800`). So either the live stack differs from HEAD or the flag is dead — **either way the advertised rollback lever is unverified, and if P-04 "removes" the flag/bypass (its literal title) the lever ceases to exist mid-change.** Rule: the revert path must be a *flip*, never a *removal*, and it must be **fire-drilled before the real deploy** — flip on, observe 401s, flip off, run the smoke harness, record the measured RTO. If the true lever turns out to be CDK route wiring, revert = full `cdk deploy` of a 476/500-resource parent + 23 nested stacks: 10–30+ minutes at 2am, not "instant." (2) **P-10**: `default_cors_preflight_options` bakes mock OPTIONS methods into an API GW *Deployment*; reverting to `ALL_ORIGINS` is a template change + redeploy of that same near-limit stack — minutes-to-tens-of-minutes, plus the Lambda-layer ACAO must revert in the same window. "Instant" is only honest if you pre-stage the revert change set (`cdk deploy --no-execute` of the rollback diff) *before* the forward deploy. (3) **Revert verification**: one scripted harness, run to green before (baseline), after deploy, and after any revert — `GET /health` via `api.dev.careervp.com` = 200 (W1); preflight with the real Amplify `Origin` echoes ACAO (W2); authenticated `GET /users/me` with a live Cognito token = 200 (W3); presigned PUT+GET round-trip from that origin (W4). A revert without a green harness run is not a revert.

- **Q3 — Runbook (validates §7's order, hardens its gates).** §7's sequence is correct; it's missing the *step-0 armor* and per-step evidence. **Step 0 (blocking, before all waves):** deploy P-12 alone — flip every `RemovalPolicy.DESTROY`→`RETAIN` (+`RETAIN_ON_UPDATE_OR_DELETE` semantics), `deletion_protection` on tables, drop `auto_delete_objects`; apply stack policy + termination protection; take golden-point snapshots; wire the deny-IAM profile for agents. *Gate:* `cdk diff` shows only policy metadata, zero replacements; harness green. **Autonomous-safe.** **Step 1:** Wave-0 nets (oracle incl. the LM-2 runtime CORS probe), P-13, P-20, P-21; LM-1/LM-2 read-only account discovery. *Gate:* evidence files committed. **Autonomous-safe** (read-only + additive). **Step 2:** P-08 then P-10, each as its own change set. *Pre-condition:* LM-2 evidence + pre-staged revert change set. *Gate:* human executes the change set; harness + real CV upload from the Amplify origin green within 10 min or revert. **Human-in-the-loop mandatory.** **Step 3:** P-04. *Pre-condition:* token-flow audit green, revert lever fire-drilled with measured RTO. *Gate:* human flips; watch CloudWatch 401 rate 30 min. **Human mandatory.** **Step 4:** P-26, blue/green: create the new RestApi *alongside* the old (never a same-deploy delete), verify via raw `execute-api` URL, human flips the base-path mapping, harness green, retire old RestApi only in a later deploy. Rollback = re-point mapping (seconds — this "instant" claim is valid *only because* the old API still exists). **Human mandatory.** P-07 stays optional-MFA.

### Risks & blind spots

- **The register understates P-26's blast radius by an order of magnitude.** It frames P-26 as "domain orphaned = site down" (recoverable). The real worst case: nested-stack decomposition moves tables/buckets across stacks, and with `RemovalPolicy.DESTROY` + `auto_delete_objects=True` a naive two-phase move **permanently deletes every table and all S3 objects in dev**. PITR's deleted-table system backup gives 35 days of grace for Dynamo; the buckets get none. P-12 must be re-classified from "🟢 first safe slice" to *mandatory precondition for P-26 and for granting any agent deploy rights*.
- **Cognito has no backup story at all — and the register omits it.** User pools cannot be exported (password hashes are unrecoverable); a logical-id rename or a decomposition move of the pool = every user permanently gone *and* W3 broken (new pool id vs. Amplify env). It needs the same stack-policy/RETAIN armor as the tables, and P-07 changes should be `--no-execute`-reviewed.
- **The Amplify-side env (the four wires) is itself unversioned clickops** — same class of land-mine as LM-1, not called out as one. Snapshot `get-app`/`get-branch` now; any revert that touches W1/W3 values must include restoring these.
- **Out-of-band CLI reverts create CFN drift**: the 2am fix (`put-bucket-cors`, env patch, mapping re-point) is silently *undone by the next routine deploy*, re-breaking the site days later. Every manual revert needs a paired "reconcile into CDK" ticket before the next deploy is allowed.
- Register omissions worth fixing: PITR window is 7 days not the assumed default; the llm-cache table has **no PITR in dev**; upload bucket is unversioned with 30-day expiry; no on-demand-backup step exists anywhere in §7; no requirement to *rehearse* any rollback before relying on it.

**Do this first (priority order):** 1) Deploy P-12 alone + stack policy + termination protection. 2) Put subagents behind the deny-`ExecuteChangeSet` IAM profile. 3) Capture the golden point: git tag, live templates, `get-base-path-mappings`/Route53 (LM-1), Amplify env, `describe-user-pool`, on-demand Dynamo backups, S3 sync of the upload bucket. 4) Build the 4-wire smoke harness and run it green as baseline. 5) Fire-drill the P-04 lever (find out what *actually* disables auth today — the repo says it isn't `AUTHORIZER_DISABLED`) and time the revert. Only then open Wave 1.

### Confidence

`high` — the load-bearing claims (DESTROY policies everywhere, `auto_delete_objects=True`, PITR=7d, single unread `AUTHORIZER_DISABLED` at `api_construct.py:1720`, COGNITO-wired routes at :2740-2800) were verified directly in the code; the only medium-confidence item is exact API GW wildcard-origin preflight behavior, which is precisely why I demand a runtime probe over a template assertion.

## 🗳️ Amplify Runtime-Seam Frontend Specialist

### Position

The register correctly locates the blast radius in W1–W4, but its two "instant rollback" claims are only half-true and it misses a fifth wire: from the runtime-seam perspective, your CORS stack is **three different matching engines** (API GW preflight VTL-regex, Lambda `cors_utils.py` exact-string set, S3 single-wildcard rules) plus static GatewayResponse headers — and the register's own suggested P-10 list `["https://*.amplifyapp.com"]` would break the live site if a subagent faithfully "keeps the Lambda ACAO in sync" with it. The only mechanical guardrail that works against a swarm is: agents get zero deploy-capable AWS credentials, and a synth-time assertion pins the **exact literal** live origin `https://ui-upgrade.d3j2wnm8g5clnw.amplifyapp.com`.

It catches an orphaned base-path mapping regardless of which layer broke.
  - **LM-2:** The wildcard is a trap. `infra/careervp/api_construct.py:834` and `cdk.json` show the Lambda layer's `ALLOWED_ORIGINS` is an **exact-match set** (`cors_utils.py`: `resolved in _ALLOWED_ORIGINS`) — `https://*.amplifyapp.com` will never match there, while CDK's preflight VTL compiles it to a regex and S3 accepts one wildcard per origin. - **A poisoned precedent (Amplify specialist only):** `src/frontend/tests/regression/cors-no-wildcard.regression.test.ts` hardcodes `['https://app.careervp.com']` — a subagent extending "existing CORS tests" will copy a list that walls out the live origin. Fix before the swarm runs.
- **Cognito is unbackupable and unlisted (skeptic + DR + CFN):** the pool has no explicit removal policy, no export path for password hashes; its stale hand-captured callback URLs (`cognito_construct.py:39-41`) prove console↔CDK drift already exists and a drift-"fixing" deploy would revert live auth. The pool must be in the stack-policy deny list and its Replacement flag checked on every Cognito-touching change set.
- **`NEXT_PUBLIC_API_URL` is baked at Next.js build time** (Amplify specialist) — repointing the FE during an incident costs a full Amplify rebuild; the base-path re-map is the only fast lever.
- **Fresh-build + template-hash pinning (skeptic):** Lambda ships from `Code.from_asset(BUILD_FOLDER)`; a stale `.build` deploys old bytes, and nothing stops agent B editing code between agent A's approved diff and the execute (TOCTOU). Hash the synth output at approval and verify at execute.
- **What no member covered:** the live-account state itself — all five flagged that the deployed stack may differ from HEAD and none could verify it. The §6 read-only evidence sweep is genuinely the first gate. Track D data-migration semantics also got only light treatment.
