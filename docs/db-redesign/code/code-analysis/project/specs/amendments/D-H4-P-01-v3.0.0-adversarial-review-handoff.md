## 1. What was decided (the thing you are attacking)

Recorded as scope-lock **v3.0.0**, 2026-07-27, MAJOR. Change-log row: `project-scope-lock.md:360`.
Proposal of record: `specs/amendments/D-H4-P-01-submit-test-conflict-amendment.md` (123 lines).
Human decision was the single token **"A1 accepted"**.

**Substance.** The interview-prep submit request contract is **tightened**:

1. `application_id` **or** `job_id` is now **required**.
2. The application-key fallback `api_request.application_id or api_request.job_id or api_request.vpr_id`
   at `interview_prep_submit_handler.py:144` is **removed**.
3. Missing identity is refused **HTTP 400 before dependency resolution** — no resolver read, no
   pending write.
4. `api_models.InterviewPrepRequest`'s written promise that *"clients that omit them continue to
   work"* is **withdrawn**.
5. `src/frontend/lib/types.ts` `InterviewPrepRequest.application_id` becomes **required**.

**Stated justification.** A client `vpr_id` standing in for the canonical application key is
legacy-id resolution, which v2.7.0/O-3 forbids; and it fed
`artifact_dependency_utils.py:183-195`, which wrote `update_artifact_status(application_id=<a vpr_id>)`
into the canonical hub behind a blanket `except Exception: return` — a silent bad write inside the
very step (D-H4) that hardens bad writes.

**Rejected alternatives** (proposal §"Rejected workaround" and the v3.0.0 row): **A2** keep the
fallback; **A3** branch on Pydantic `model_fields_set` to accept omission but reject explicit null;
**A4** resolve `vpr_id → application` through the repository.

## 2. The four attacks worth making

Attack these specifically. Each is a place the amendment could still be wrong, and each is phrased so
that a *finding* is possible — not just an endorsement.

### Attack 1 — Is MAJOR the right semver, or is this over-classified?

The row **concedes the counter-argument itself**: *"by the letter of §0.3 this could be read MINOR
(refine a `TARGET` — P-01 and D-H4 are both `TARGET`, and none of the ten §3 items is broken); MAJOR
was chosen deliberately as the conservative classification."*

Check against §0.3's semver ladder (`:35-38`). MAJOR = *"change an IMMUTABLE invariant or locked
decision; drop a feature; break a frontend-contract item."* Ask:

- Is a **comment** in `api_models.py` promising omission-tolerance actually a "frontend-contract
  item" in §3's sense, or is §3's enumerated ten-item list the only contract surface that counts?
- Does over-classifying cost anything real? (Consider: a MAJOR release is a governance signal;
  inflating it dilutes the signal, and the row's own §12 precedent for MAJOR is v2.0.0's A8, where a
  *downstream-consumed guarantee* was relaxed. Is this comparable, or materially smaller?)
- Conversely: is there an argument it is *more* than MAJOR — e.g. that it should not have been an
  agent-executed amendment at all under §0.3's write-protection note?

A finding of "should be MINOR" is a real, useful outcome. So is "MAJOR is right, for this reason the
row does not state."

### Attack 2 — Is the "safe for shipped callers" evidence actually complete?

This is the load-bearing empirical claim. The proposal asserts no shipped caller omits both
identifiers, citing:

- `src/frontend/app/applications/[id]/page.tsx:126` — creates the hook with the page's `jobId`
- `src/frontend/hooks/useGenerateModule.ts:69-73` — sends `application_id: jobId`
- *"repository-wide search finds no second direct `generateInterviewPrep` caller"*
- `InterviewPrepRequest` is **not** in `scripts/emit_json_schemas.py` `CONTRACT_MODELS`, so no
  committed oracle schema regenerates

**Verify every one of those live — do not take them on trust; one citation in this proposal was
already found stale** (it admits `app/dashboard/jobs/[jobId]/page.tsx:354-357` "does not exist in the
current tree"). Then push past what it checked:

- The frontend is **one** client. Is it the **only** one? Check for mobile clients, Postman/HTTP
  collections, integration or e2e tests that hand-roll the request body, `curl` in docs, smoke
  harnesses (`scripts/`), and the P-30 4-wire harness.
- Are there **cached or in-flight** clients? The frontend bakes config at build time (see the P-26
  clause's `NEXT_PUBLIC_API_URL` discussion) — can a browser running yesterday's bundle still send
  the old shape, and what does it now get? A 400 where it used to get 202 is a user-visible
  regression even if the current source is fine.
- Is there a **deployed** stack still serving the old frontend build? Note `CareerVpCrudDev` and
  `CareerVpCrudDevx` are both live.

### Attack 3 — Was A3 (`model_fields_set`) dismissed too fast?

The proposal rejects it as *"compatibility machinery renamed."* Steelman it instead: it is the only
option that distinguishes *"the client forgot"* from *"the client explicitly sent null"*, which are
genuinely different intents. Then decide whether O-3 really forbids that distinction, or whether the
proposal is reading O-3 more broadly than it says. Read O-3's actual text (`project-scope-lock.md:328`
and the v2.7.0 amendment section) rather than the proposal's paraphrase.

### Attack 4 — Does the affected-test inventory now hold, and is the root defect actually fixed?

The amendment's own **root defect** is that the RED brief carried no affected-existing-test inventory,
so `test_async_submit_handlers.py` was never reconciled before RED landed. 3.2-GREEN then found **8**
affected tests, having inventoried **1** — the other 7 surfaced only by running the full suite (1 in
`test_async_submit_handlers.py`, 5 fed by the shared `_valid_request_body()` helper in
`test_interview_prep_roundtrip.py`).

- Is the inventory now in `specs/D-H4-P-01-canonical-artifact-spec.md`, and is it **complete**?
- Were those 7 reconciled as *approved contract updates*, or were any effectively **weakened**?
  §9.3 hard-rejects *"a test weakened to pass."* Read the actual diffs; do not accept the ledger's
  self-report.
- Is the process fix real — will the next RED brief carry an inventory, or is that only a note in one
  spec?
