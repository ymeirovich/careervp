## 4. Constraints

1. **Report; do not fix.** The deliverable is your assessment. Do not edit any file — not
   either scope-lock twin, not the governing spec, not any test, not any handler. Do not
   apply a fix even where one is obvious and small, and do not create branches, stashes, or
   backup copies. If you conclude something must change, say what and why, and stop.
2. **Never edit `tests/unit/test_dh4_p01_canonical_artifact.py`.** It is the pinned RED
   test. Criticising it is in scope; touching it is not, under any circumstance.
3. **Live truth wins.** Scope-lock §0.2 ranks running code and command output above any
   static claim. At least two citations in this amendment's paper trail are already known
   to be wrong. Verify from the code and from commands you run — including the claims in
   this file.
4. **Ground every claim in a tool result from this session.** Before you report a finding,
   audit it against something you actually ran or read. Report only what you can point to
   evidence for; where something is unverified, say so explicitly and say why. If a test
   fails, quote the output. If a step was skipped, say it was skipped. When something is
   confirmed, state it plainly without hedging.
5. **Genuine dissent is the deliverable.** `eval-council-prompt.md:205` treats zero
   disagreement on a same-model panel as a failed run. If you agree with round 1 entirely,
   you must still name the strongest surviving objection to *your own* conclusion and
   explain why it fails.
6. **Stay inside this amendment.** D-H7/3.3, 3.4 and 3.5 are not yours. The
   `artifact_cleanup_handler.py:188` bug and the `entity_type-index` dead read path are
   known, recorded, and out of scope. Note in passing anything you trip over; do not
   investigate it.

## 5. How to work

Delegate. This is a wide verification problem across specs, twins, handlers, two frontend
trees, several test suites, and git history — fan independent tracks out to sub-agents and
keep working while they run, rather than walking it serially. Intervene when a sub-agent
goes off track or is missing context it needs. Commit to what you delegate: do not re-derive
a sub-agent's findings once it reports, and do not take a sub-agent's report at face value
where it makes a load-bearing claim without evidence — a sub-agent that reports a conclusion
without a command behind it has given you a hypothesis.

If you want a scratch file for findings as they accumulate, write it under the session
scratchpad, not into the repository.

## 7. Writing the final summary

This will run long and largely unattended, and the person reading your summary did not watch
the trace. Terse shorthand between tool calls is fine — that is you thinking out loud. The
final summary is different: it is their first look at any of it, so write it as a
re-grounding rather than a continuation of your working thread.

Lead with the outcome — the first sentence should answer what you found and what you
recommend. Supporting detail after. Drop the vocabulary you built up while working unless you
re-introduce it. Write complete sentences; spell terms out; no arrow chains, no
hyphen-stacked compounds, no labels you invented earlier. When you mention a file, commit,
flag, or clause, give it its own plain clause saying what it is — never pack several into one
parenthesised run. Being readable and being concise are different things, and readable
matters more: keep it short by being selective about what you include, not by compressing the
prose.
