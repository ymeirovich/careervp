### Background: What CareerVP Is Supposed to Do

CareerVP is a job application assistant. A user uploads their CV, pastes a job description,
and the system automatically generates:
1. **Gap Analysis Questions** — targeted questions about missing experience
2. **Value Proposition Report (VPR)** — a strategic analysis of the candidate's fit
3. **Tailored CV** — the user's CV rewritten for the specific job
4. **Cover Letter** — a persuasive letter referencing the VPR analysis
5. **Interview Prep** — predicted interview questions with STAR responses

Each of these is generated by a separate AI agent (a Lambda function that calls Claude). The
architecture document (`docs/architecture/prompt-improvement/CareerVP_Agentic_Architecture.md`)
describes the full 7-agent pipeline.

### What Is Currently Broken (Plain English)

**Problem 1 — The AI key is missing:**
Every Lambda function that calls the Claude AI API needs an API key. That key is not set in
any of the Lambda environments. When a Lambda tries to connect to Claude, it immediately fails.
Instead of returning an error, the handlers silently return a hardcoded fake response (called a
"fallback"). This is why gap questions say "Describe a measurable achievement relevant to
`56847430-6433-4144-a41e-f112f570003e`" — it's a template with a job ID pasted in.

**Problem 2 — The database queries are broken:**
When you call `GET /jobs` or `GET /vprs`, the code queries a DynamoDB index called
`user_id-index`. That index was never created in the database setup scripts. So every query
silently fails and returns an empty list — even though the jobs and VPRs were created and stored.

**Problem 3 — Two different tables for the same data:**
When a CV is uploaded, it gets saved to Table A. When you list CVs, the code reads from
Table B. These are different tables with different key structures, so the list always returns empty.

**Problem 4 — Wrong authentication system:**
The login endpoint creates a custom security token. But the API Gateway (the front door that
routes requests to Lambdas) only accepts tokens from AWS Cognito (a managed auth service).
So custom tokens from `/auth/login` are rejected before they even reach the Lambda — giving
`401 Unauthorized` on every protected route.

## 1. Executive Summary

The live test suite (live-test-results10.log) reveals **3 failed test modules**, **2 skipped tests**,
and **5+ endpoints returning empty lists** despite data having been previously generated. The failures
fall into four root-cause categories:

| Category | Count | Impact |
|---|---|---|
| Missing DynamoDB GSI (`user_id-index`) | 1 | Breaks GET /jobs, GET /vprs |
| Table/schema wiring mismatches | 3 | Breaks GET /users/me/cv, GET /gap-questions, GET /cover-letters |

Gap Analysis → VPR → CV Tailor / Cover Letter / Interview Prep → Quality Validator). The current
API has all the agent handlers deployed but they are **silently failing** because the AI key is
absent and infrastructure wiring is wrong.

**This plan has zero new features.** Every change is a fix or a wiring correction to make the
existing code work as designed.

## 3. Root Cause Analysis

### 3.1 CRITICAL: Missing `user_id-index` GSI on jobs_table

**Files:**
- [api_db_construct.py:220](../../infra/careervp/api_db_construct.py) — jobs_table definition
- [jobs_repository.py:27,130,145](../../src/backend/careervp/dal/jobs_repository.py) — queries

**What happens:**
`GET /jobs` calls `jobs_repository.get_jobs_by_user()` which queries `IndexName='user_id-index'`.
`GET /vprs` calls `jobs_repository.get_vpr_jobs_by_user()` which queries the same index.
The jobs_table in CDK only defines `idempotency-key-index`. The `user_id-index` GSI does not exist.
Both methods catch `ClientError` and silently return `[]`.

**Observed:** Every job and VPR created successfully, but GET /jobs and GET /vprs always return empty arrays.

**Fix:** Add `user_id-index` GSI to jobs_table CDK definition and update IAM policy.

---

### 3.2 CRITICAL: CV Table/Key Mismatch

**Files:**
- [cv_upload_handler.py:181](../../src/backend/careervp/handlers/cv_upload_handler.py) — writes to `TABLE_NAME`
- [user_handler.py:126](../../src/backend/careervp/handlers/user_handler.py) — reads from `CVS_TABLE_NAME`

**What happens:**
Upload saves CV via `DynamoDalHandler` to `TABLE_NAME` using `pk`/`sk` single-table keys.
List reads from `CVS_TABLE_NAME` (a different table) using `Key('userId').eq(user_id)` (camelCase, different schema).
These are two completely different tables with two different key schemas. A CV uploaded to one can never be found by a query to the other.

**Observed:** POST /users/me/cv → 201 Created with cv_id. GET /users/me/cv → `{"cvs": [], "cursor": ""}`.

**Fix:** Unify on a single table. Either: (a) make `_list_user_cvs()` read from the same table/key as upload, or (b) fix the upload path to write with the `userId`/`cvId` schema that the list expects.

---

### 3.3 CRITICAL: ANTHROPIC_API_KEY Not Set in Lambda Environments

**Files:**
- [llm_client.py:40,43,50](../../src/backend/careervp/logic/llm_client.py) — key resolution
- [api_construct.py](../../infra/careervp/api_construct.py) — Lambda environment blocks

**What happens:**
`_get_anthropic_client()` tries `os.environ['ANTHROPIC_API_KEY']` first, then SSM via
`ANTHROPIC_API_KEY_SSM_PARAM`. If neither is set, raises `ValueError`.
All handler exception paths return a hardcoded fallback response (gap questions, cover letter, etc.)
with `"warning": "ANTHROPIC_API_KEY not found in environment or SSM"`.

**Observed:** Every AI-powered endpoint returns template/fallback output. Gap questions say "Describe a measurable achievement relevant to {job_id}."

**Fix:** Add `ANTHROPIC_API_KEY` or `ANTHROPIC_API_KEY_SSM_PARAM` to ALL agent Lambda environment variable blocks in api_construct.py.

### 3.4 CRITICAL: Gap Handler Fallback Does Not Persist Questions

**Files:**
- [gap_handler.py:127-142](../../src/backend/careervp/handlers/gap_handler.py)

**What happens:**
The happy path calls `dal.save_gap_questions()` then returns questions.
When any exception occurs (including the ANTHROPIC_API_KEY error), the `except Exception` block at
line 127 returns a hardcoded question WITHOUT calling `dal.save_gap_questions()`.
The response uses HTTP 201 CREATED (same as success) with a `warning` field instead of `error`.
Subsequent GET /gap-questions queries DynamoDB and finds nothing → returns `[]`.

**Secondary issue:** The fallback question text interpolates the raw job UUID: `f"Describe a measurable achievement relevant to {job_id}."` — exposing internal IDs to users.

**Observed:** POST /gap-questions → 201 with `warning`. GET /gap-questions → `{"questions": []}`.

**Fix:** On failure, either (a) surface the error properly with 4xx/5xx, or (b) persist the fallback questions so GET can return them. Fix (a) is preferred.

### 3.5 HIGH: Gap Lambda `DYNAMODB_TABLE_NAME` Points to Wrong Table

**Files:**
- [api_construct.py:1668](../../infra/careervp/api_construct.py)

**What happens:**
Gap Lambda's `DYNAMODB_TABLE_NAME` env var is set to `artifacts_table.table_name`.
`artifacts_table` has schema `PK=applicationId, SK=artifactId`.
`gap_responses_table` has schema `PK=userId, SK=questionId` — which is what the gap handler expects.

**Fix:** Change line 1668 to point `DYNAMODB_TABLE_NAME` to `gap_responses_table.table_name`.

### 3.8 HIGH: Auth Mismatch — Custom JWT vs Cognito Authorizer

**Files:**
- [auth_service.py:265-281](../../src/backend/careervp/logic/auth_service.py) — mints JWT with `user_id` claim
- [auth_utils.py:28-47](../../src/backend/careervp/handlers/auth_utils.py) — reads Cognito `sub`
- [api_construct.py:1771](../../infra/careervp/api_construct.py) — Cognito authorizer on all protected routes

**What happens:**
`auth_service.py` mints RS256 JWTs with a `user_id` claim (not `sub`).
API Gateway uses a `CognitoUserPoolsAuthorizer` which validates Cognito tokens, not custom JWTs.
Custom JWTs from `/auth/login` are rejected at the Gateway before reaching any handler.
`auth_utils.py` reads Cognito `sub` from the authorizer context — which is never populated for custom JWTs.
The `x-user-id` header fallback (Path 3 in auth_utils) is the only working path — but is insecure because any client can forge it.

**Observed:** Contract test sends token from `/auth/login` to GET /users/me → 401 from API Gateway.

**Fix options:**
- **Option A (preferred):** Replace `AuthService` internals with Cognito `sign_up`/`initiate_auth`. Keep response contracts identical. Protected routes then receive real Cognito JWTs.
- **Option B (temporary):** Wire the deployed JWT Lambda authorizer (currently dead code at api_construct.py:1618-1645) as API Gateway's token authorizer instead of Cognito. Less work but deviates from the designed infrastructure.

### 3.9 MEDIUM: Cover Letter Handler Silent Fallback

**Files:**
- [cover_letter_handler.py:113-130](../../src/backend/careervp/handlers/cover_letter_handler.py)

**What happens:**
If CV load fails OR generation raises any exception, handler returns HTTP 200 with a synthetic
`artifact_id = f'cover-letter-{job_id}'` and `"status": "completed"`.
Nothing is written to DynamoDB. `GET /cover-letters` returns `[]`.
`GET /cover-letter/{id}/status` returns a generic boilerplate letter.

### 3.10 MEDIUM: CV Tailoring ID Shape Inconsistency

**Files:**
- [cv_tailoring_handler.py:251-293,534](../../src/backend/careervp/handlers/cv_tailoring_handler.py)

**What happens:**
Request ID written as `cv-tail-<uuid>`. SK written as `ARTIFACT#CV_TAILORED#cv-tail-<uuid>`.
List endpoint at line 534 returns `item.get('request_id') or item.get('sk')`.
Older records without `request_id` return the full prefixed SK as the external `id`, producing
`ARTIFACT#CV_TAILORED#...` format visible to clients.

**Fix:** Always store `request_id` attribute on every record. List always reads from `request_id`.

## 10. Compliance Notes

All fixes must comply with `docs/best_practices/`. Key requirements:

1. **No hallucinations in AI output:** Agents must use only CV facts + gap responses (not invented data)
2. **Error responses must be explicit:** No silent swallows; 4xx for client errors, 5xx for server errors
3. **DynamoDB key consistency:** All operations on the same logical entity must use the same PK/SK schema
4. **IDs must be stable and canonical:** External IDs returned to clients must be the same on read as on write
5. **AI key must be resolved before Lambda runs:** Do not swallow `ValueError` from `_get_anthropic_client()`; surface it as a 503
6. **Anti-AI detection patterns:** Cover letter and VPR outputs must follow the banned-words list and style rules
7. **Fact verification:** VPR and CV outputs must only include facts verifiable from CV or gap responses
8. **Cost tracking:** Each agent Lambda should track tokens used and estimated cost in DynamoDB application record
